=== PAGE 3 ===
1. Executive Summary
Naweza Consulting needs one credible, mobile-first brand website that represents two legal entities — Naweza Investments CC
(established 2018, the track record) and Naweza Consulting Investments (Pty) Ltd (established 2026, the international/Africa market-
development arm) — without legally merging them or overstating the Pty Ltd's history. The brief also flags a clear future path: consultation
booking, service-specific forms, document upload, quotations, payments, a client portal, and CRM/lead capture. 
Because content (services, case studies, insights, entity wording) will change often and the site must grow into transactional features, the
recommended approach is a headless, API-first architecture: a Next.js front end on Vercel, a headless CMS for everything editorial,
and a managed Postgres database reserved for anything transactional (bookings, leads, users) added in later phases. This lets Phase 1
ship as a fast, content-only marketing site, while Phases 2–3 add features by extending the same codebase rather than replacing it.

3. System Architecture
Architecture is layered so Phase 1 only needs the top two layers; Phase 2–3 activate the rest without touching the front end's
structure.
Edge / CDN — Vercel — serves static and ISR-cached pages globally, routes requests, handles domains & SSL, runs middleware (redirects,
locale, security headers).
▲▼
Application — Next.js (App Router, TypeScript) — renders Home / About / Services / Africa Market Development / Case Studies / Insights /
Booking / Contact. Server Components pull content at build time or via ISR; Client Components handle interactive forms.
▲▼
Content layer
Sanity.io — services, case studies, insights, entity/legal copy,
homepage sections. Editors update content without a deploy.
API / server actions
Next.js API routes — contact/booking form submission, quotation
requests, webhook receivers (Stripe, Cal.com).
▲▼
Transactional data — Phase 2+
Postgres (Neon/Vercel Postgres) via Prisma — bookings, quotation
requests, leads, uploaded-document metadata.
Third-party services
Stripe (payments) · Cal.com (scheduling) · Resend (email) · Clerk/
Auth.js (Phase 3 portal login) · CRM (HubSpot/Pipedrive, Phase 3)
Request flow example — "Book a Consultation" (Phase 2)
Visitor fills the booking form (React Hook Form + Zod validation) on a page served from the Edge.
Form posts to a Next.js Server Action / API route.
The route writes the request to Postgres, triggers a Resend confirmation email to the client and a notification to 
bookings@nawezaconsulting.com , and (if using Cal.com) creates the calendar event.
If the engagement requires payment, the client is redirected to a Stripe Checkout session; Stripe's webhook confirms payment back
to the API route, which updates the booking status.
Everything left of "Postgres" in this flow does not exist yet in Phase 1 — the Phase 1 site only needs a simple contact/enquiry form that emails the team.

=== PAGE 8 ===
6. Brand & Entity Presentation Rules
These are hard content rules from the brief. They should be enforced structurally (via the CMS schema above), not just remembered
by whoever edits copy.
One public brand: NAWEZA CONSULTING. The two legal entities are never presented as "merged."
Naweza Investments CC — established/operating since 2018. This is the only entity allowed to carry the 2018 track record and the
three named case studies.
Naweza Consulting Investments (Pty) Ltd — established 2026. Must never be described or implied as operating since 2018. Owns
the Africa Market Development positioning.
Do not invent additional clients, statistics, awards or credentials anywhere on the site.
The Pty Ltd is not presented as "registered" until registration is actually complete; once it is, registration details are added to the
footer/legal/contact area (this is exactly what the isRegistrationComplete  / registrationNumber  fields above are for).
Formal documents generated from the site in future phases (quotations, invoices, agreements) must identify the correct contracting
entity per engagement — this becomes a required field on the BookingRequest / quotation data model in Phase 2.
International outreach (e.g. LinkedIn) can reference the Pty Ltd's 2026 identity immediately; it does not need to wait for the website.

10. Scalability & Performance Plan
Static + ISR rendering: marketing pages (services, case studies, insights) are statically generated and revalidated on a schedule or
on CMS webhook, so traffic spikes hit Vercel's CDN cache, not the origin.
Images: Next.js Image component with automatic resizing/format conversion (AVIF/WebP) — important given the photography-heavy
design direction.
Serverless functions for forms/bookings scale automatically with Vercel — no server capacity planning needed.
Database scaling (Phase 2+): Neon/Vercel Postgres support connection pooling and autoscaling compute, so the same database
serves the site from first booking through hundreds per month without a migration.
Preview deployments: every content or code change gets its own URL to review before it reaches the live domain — useful when
an agent is doing the building.
11. Security, Compliance & Ops
HTTPS everywhere (automatic via Vercel), HSTS and standard security headers via Next.js middleware.
Form spam protection (e.g. Cloudflare Turnstile or hCaptcha) on public forms from Phase 1 onward.
Least-privilege environment variables for all API keys (Sanity, Stripe, Resend, database), managed in Vercel's encrypted project
settings — never committed to the repo.
Document uploads (Phase 2) stored in access-controlled storage (Vercel Blob/UploadThing) with signed URLs, not public buckets.
Client portal auth (Phase 3) uses a managed provider (Clerk/Auth.js) rather than custom-built authentication.
Formal documents (quotations, invoices) must be generated with the correct legal entity attached — a data validation rule, not just a
content reminder.

12. Deployment Plan (Vercel)
Create the GitHub repository; connect it to a new Vercel project.
Configure three environments: Production (nawezaconsulting.com), Preview (automatic per pull request), Development (local).
Point the domain's DNS to Vercel; configure MX/DKIM/SPF records separately for Google Workspace or Microsoft 365 email —
domain hosting and email hosting are independent and both need to be set up.
Provision Sanity project and connect via environment variables; seed initial content (services, case studies, legal entities) from this
document's Section 5 schema.
Set up Vercel Analytics/Plausible, and error monitoring (e.g. Sentry) from day one.
Phase 2: provision Neon/Vercel Postgres, Stripe account, Resend account, Cal.com; add corresponding environment variables and
webhook endpoints.
Phase 3: provision Clerk/Auth.js and CRM integration.
13. Open Questions Before Build
1. Has the domain (nawezaconsulting.com) already been registered, or does that need to happen as step one?
2. Preferred email platform — Google Workspace or Microsoft 365 — for info@/bookings@/etc.?
3. Is there existing photography (founder/team, case-study projects with permission) or does Phase 1 need a stock-image sourcing pass first?
4. Target date for Pty Ltd registration completion, so the Section 6 entity rules and footer can be updated on schedule?
5. Should Phase 1 include a CRM/mailing-list signup even before full CRM integration (Phase 3), to start capturing leads immediately?
6. Any existing brand guideline (logo files, exact colour hex codes) beyond "corporate blue, black, white, off-white," or is the palette in Section 7
final?
7. Budget/timeline constraints for Phase 1, so the agent can be scoped against a realistic delivery window?
